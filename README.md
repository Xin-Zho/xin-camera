# xin-camera

iPhone 回忆 App —— 第一阶段可交互原型。

按地点与时间组织照片记忆：地图 + 竖向时间轴浏览地点，点开地点看到访卡片堆叠，
再进到那一次到访的图库；另一条线是杂志式的「故事相册」。

- 技术栈：Expo SDK 58 · React Native 0.88 · TypeScript · Expo Router · react-native-maps · Zustand
- 开发机：Windows；预览：iPhone + Expo Go
- 数据：24 张项目内示例图 + **可导入真实相册照片**（只读相册，不上传、不改原图）。
  没有后端、没有 AI、没有云端同步。

## 跑起来

```powershell
cd D:\xin-camera
npx expo start
```

iPhone 与电脑连同一个 Wi-Fi，用 Expo Go 扫终端二维码。
Android / iOS / Web 之外的平台没有验证过，Web 上地图不可用（react-native-maps 无 web 实现）。

> 注意：本项目是 **SDK 58**。手机上的 Expo Go 必须支持 SDK 58，
> 否则会提示版本不兼容，此时请升级 Expo Go。

## 照片可见性（M12）

**「这张照片还该不该显示」只有一个答案，写在 `src/domain/visibility.ts`。**
地图、到访图库、故事阅读页、编辑页、设置页都从这一个函数取快照，不再各写一套 `filter`。

判定顺序不可交换：

| 顺序 | 条件 | 结果 |
|---|---|---|
| 1 | `media.removedAt` 有值 | 隐藏。原因 `removed`。**用户移除优先于一切**，故事还在也不显示 |
| 2 | 被至少一本**活跃故事**引用 | 显示。活跃 = 没删（`isDeleted`）且没被合并走（`mergedIntoStoryId`） |
| 3 | 引用它的故事都删了 / 都并走了 | 隐藏。原因 `story-deleted` |
| 4 | 没有任何故事引用 | 隐藏。原因 `unlinked`（脏数据或导入中断的残留，不能因为「没主」就露出来） |

由此得到的联动，都不需要额外代码：

- **删故事** → 它独占的照片变 `story-deleted` → 到访没有可见照片 → 地图标记消失、时间轴收缩；
  被其他故事共用的照片照常显示（判定按引用算，不是按「哪本先删」算）。
- **恢复故事** → 照片重新可见 → 地图标记回来、时间轴扩回来。
- **地点一张可见照片都不剩** → `selectMapPlaceSummaries` 直接不返回它，标记隐藏；
  地点页仍可进入（到访为空时给说明文案），数据没有删。
- **全部隐藏** → 时间轴没有刻度、地图显示空状态卡片，**不回退示例数据**
  （`merge` 只认存档损坏，不认「空」）。

**从图库移除照片**（`visit/[visitId].tsx`）：右上角「选择」或长按照片进入选择模式 → 多选 →
「从回忆相册移除」。确认弹窗写明**只在本 App 内隐藏，iPhone 系统相册的原图不会被删除**。

**移空自动删除**（真机验收后确认的产品逻辑）：故事的照片被全部移除后，故事自动进「已删除」
（打 `deletedByEmptying` 标记）；恢复其中任何一张照片，故事自动回来。
手动删除/手动恢复一律清标记——手动删除后恢复照片不复活故事。

只写 `MediaAsset.removedAt`，**不动** `story.mediaIds` / `visit.mediaIds` / `place.mediaIds`：
引用留着，恢复时顺序、封面位置、精选标记全都原样回来。封面被移除时读取侧回退到第一张可见照片
（`pickVisibleCover`），字段本身不改——用户恢复那张之后，封面还是它。

恢复有两条路：

1. 到访图库底部的「已移除 N 张」区，逐张恢复（就地恢复，不用跳页）；
2. 设置 → 回忆相册 →「已移除的照片」（`app/removed.tsx`），按移除时间倒序，支持逐张和全部恢复。

第二条不是冗余：某次到访的照片**全部**被移除后，那张到访卡片就从地点页消失了，
用户再也进不去那个图库——恢复入口会跟着一起被藏掉。

**重复导入不会让已移除的照片复活**：去重键仍是 `libraryAssetId`，而 `media` 记录一直在
（只是多了 `removedAt`），所以再导一次会被判重跳过，`removedAt` 保持不动。恢复只能走上面两条路。

## 时间轴跟随有效照片

刻度范围不再从到访取最早/最晚，也不再被示例数据的跨度撑住——只由**当前有效照片的归属日**决定，
导入 / 删除 / 恢复 / 移除照片之后立刻重算（`withReconciledRange`，在每个会改变可见集合的 action 里调用）。

粒度跟着跨度走，不是固定的：

| 跨度 | 刻度 | 标签 |
|---|---|---|
| ≤ 31 天 | 按日 | `10月12日` |
| ≤ 24 个月 | 按月 | `10月`；跨年时 1 月那格显示 `2026` |
| 更长 | 按年 | `2026` |

两条容易忽略的细节：

- **刻度范围与照片归属日用同一套口径**（`rangeKeyOf` / `isDayKeyInRange`）。
  照片的归属日是 `2026-10-12`，它就只属于 10 月 12 日那一格。
  旧实现是「时刻区间求交」，跨午夜的到访会同时出现在两格里，时间轴计数和地图标记数对不上。
- **选中时间超出新范围时自动收回**（`reconcileRangeToSpan`）：落到离原位置最近的刻度。
  删掉最新一批就退到新的最晚一格，删掉最早一批则原地不动。

## 时间轴几何（M13）

时间轴上的「哪个 ratio 落在哪个高度」之前有三套算法，真机上的表现是
**底部对齐、越往上越偏**（详见 `docs/v6-rail-geometry.md`）：

| 谁 | 之前 | 现在 |
|---|---|---|
| 刻度 | `bottom: ratio × 100%` + `paddingVertical: 16` | `tickBottom(ratio, 高度)` 像素 |
| 滑块 | `translateY(-ratio × 整个轨道高度)` + `marginBottom: -13` | `thumbTranslateY(ratio, 高度)`，布局改 `top: 0` |
| 拖动 | `y / 整个轨道高度` | `ratioForTouchY(y, 高度)` |

三者现在只认 `src/components/timeline/railGeometry.ts`：起点 = 顶部内缩，
终点 = 底部内缩，有效高度 = `高度 − 2 × 内缩`，**一律像素，不再出现百分比**。
百分比的解析盒在原生（内容盒，`YGErrataAll` 含 `AbsolutePercentAgainstInnerSize`）
和 Web（padding 盒）不一样，这就是偏 32px 的来源——现在两边都按同一套像素算，
Web 与原生必然一致。

顺带：滑块不再半个探出卡片外，刻度不再超出竖线两端。

## 本地持久化

**四层一起存**（`stories` / `places` / `visits` / `media`），版本 `STORE_VERSION = 2`。
v1 只存故事层，是因为原型里用户能改的只有故事那一层；照片导入会新建地点、到访和媒体，
不一起存就会「导入成功了，重启后照片全没了」。

- 存档键 `xin-camera-store`，改结构时版本 +1 并在 `migrate` 里补一条迁移。
- **进存档的**：
  - `stories` 全量，含 `isDeleted`、`mergedFromStoryIds`、`mergeSnapshot`。
    `mergeSnapshot` 必须一起存——不然重启后合集还在但拆不回去了；
  - `places` / `visits` / `media` 全量。导入的照片 `uri` 是真实 `file://` 路径，
    存下来有意义（示例素材是 `mock:<slug>` 键，跟着素材表走）。
- **不进存档的**：`timeRange`、`selectedPlaceId`、`selectedVisitId`、`lastMergedStoryId`、`mapFocus`。
  这些是瞬态 UI 状态，重启回到"最近一次回忆所在月份"比恢复上次拖到的位置更符合预期。
- **结构校验**：`merge` 时每层各过一个校验函数（`isValidStory` / `isValidPlace` /
  `isValidVisit` / `isValidMedia`），任一层不合格就整层丢弃。
  故事一条都留不下就当存档坏了，整体回退示例数据——空相册比丢一次编辑更糟。
- **v1 存档兼容**：v1 里不可能有后三层，`migrate` 只交出 `stories`，三层由 `merge` 用示例数据补齐。
  声明了四层却有空层（手改过的 JSON）走隔离备份，不返回半截对象。
- **启动不闪**：`app/_layout.tsx` 等 `persist.hasHydrated()` 再渲染路由树，另设 1.2s 兜底，
  避免"存档还没读完先按示例数据画一帧"导致改过的标题闪回旧值。
- **存不了也不崩**：`safeStorage` 把 AsyncStorage 的读写都包了 try/catch，原生模块缺失时降级为内存态
  并打一条 warn，不让启动流程抛错。
- 重置入口在设置页底部（`resetToMock`，带二次确认），重置后存档立刻被示例数据覆盖。

### 存档坏了怎么办

两种失败要分开，因为用户能做的事不一样：

| 情况 | 判定位置 | 界面 | 数据 |
|---|---|---|---|
| 存储不可用（原生模块缺失等） | `safeStorage` 抛错 / 读取失败 | 设置页红条：**当前修改仅在本次运行有效** | 无法保存，退出即回到示例数据 |
| 存档不是合法 JSON | `safeStorage.getItem` 预解析失败 | 设置页黄条 + 「查看备份」 | 原样抄到 `xin-camera-store__quarantine`，本次用示例数据 |
| JSON 合法但一条可用故事都没有 | `merge` 校验后为空 | 同上 | 同样备份原始文本 |

关键点：**坏存档不能被示例数据直接覆盖**。如果什么都不做，zustand 回退到示例数据后，
下一帧 `persist` 就会把整份坏存档写成新的示例 JSON，用户攒的标题和合并记录彻底没了。
所以 `getItem` 在把 `null` 返回给 persist 之前先抄一份到隔离区，隔离区只有 `quarantine.tsx`
页面的「删除这份备份」能清掉。备份存的是**原始文本**，不是解析后的对象——后者已经是"我们以为它是什么"。

## 真实相册：读取与导入

独立入口（故事页右上角「相册」/ 设置页），和示例数据那条线**在数据层隔离**：
示例地点/故事永远不参与导入的距离匹配与追加，导入产生的记录带 `origin: 'library'`。
相册本身只读，不修改、不删除。

### 读取

- 用 SDK 58 的**类式 API**（`Query` / `Asset`）。`expo-media-library/legacy` 从默认入口导入会**运行期抛错**，不是警告。
- 列表页一次拿全的只有「时间和类型」：`Query.exeForMetadata()`。**定位和缩略图必须逐条补**
  （`Asset.getLocation()` / `Asset.getUri()`），所以页大小固定 24，第一页自动读、后续每页用户点。
- **`creationTime` 是毫秒，但类型注释写的是秒。** iOS 实现 `Date.millisecondsSince1970` 才是真的。
  处理方式是原值照存 + 按数值量级判定单位（`src/library/epoch.ts`），界面把原始值和判定结果一起显示。
- **相册 API 不提供拍摄地时区。** `getLocation()` 只有经纬度；只有 EXIF 里可能残留
  `OffsetTimeOriginal`，且读取代价高（导出临时文件 + 可能触发 iCloud 下载）。详见 `docs/v2-photo-library.md`。
- 权限分六档：未决 / 全部 / 部分 / 已授权但宿主不区分范围 / 拒绝 / **原生模块缺失**。
  最后两档在界面上是两回事，不能混成"没有权限"。
- **视频只做到「能识别，不导入」**，不等于视频功能已验收。列表里给的是明确的占位卡
  （深底 + 播放图标 + 「视频」文字，有时长就带时长角标），不是空白——空白会被当成加载失败。
  导入时会过滤掉非照片，结果面板单列「跳过 N 个视频」。

### 导入

规则全在 `src/library/importPlan.ts`（纯函数），落库在 `appStore.importLibraryAssets`。
完整规则与限制见 `docs/v4-import.md`，这里只列会改变用户认知的几条：

- **有定位**：80 m 内并入已有导入地点，否则新建；地点名默认 `未命名地点 N`（没做逆地理编码）。
- **无定位**：全部收进「未定位」一处（固定 id，`unlocated: true`），地图标记与时间轴过滤掉它，
  照片不丢、故事照看。**未定位不参与距离匹配**——几内亚湾附近拍的照片不会被并进去。
- **切分**：同地点 + 同归属日 + 间隔 ≤ 4 小时算一次到访。`dateKey` 优先于间隔：
  23:30 和次日 00:30 只差 1 小时也会切成两本。第二本起标题加当地时刻后缀。
- **重复导入**：以 `libraryAssetId` 为数据源键跳过。一行新的都没有时**完全不写 store**。
- **不覆盖用户编辑**：`editedByUser` 的故事、已删除的、已合并的、以及孤儿到访，
  一律不追加，另起一本——追加会打乱用户排好的封面和顺序。
- 导入后地图会**自动归位**到第一个有定位的新照片处，并把时间窗口切到那个月，否则新内容在屏幕外。

## 日期归属口径（M10 / M11）

规则实现在 `src/library/dateRule.ts`（纯函数），验证页面是「相册 → 日期口径验证」。

目标是**旅行照片回到国内后仍归在拍摄当地那一天**。三个来源按可靠性取第一个可用的：

1. EXIF 声明偏移（`OffsetTimeOriginal` 等）→ 叠加在 `creationTime` 上算日；
2. EXIF `DateTimeOriginal` 的日期部分（相机写的当地墙上时间）；
3. 都没有 → 回退设备时区，来源标记为 `device-tz`，界面上是橙色标签，不伪装成准确值。

关键判据是**反推偏移**：`wallClockAsUtcMs(DateTimeOriginal) - creationTime`。它能验证
`creationTime` 有没有被按设备时区规范化过——如果一张海外照片的反推偏移等于设备偏移，
说明系统在落库时把墙上时间当设备时区解释了，这是个必须知道的坏消息。
反推值必须**落在 15 分钟粒度上**才算现实时区，`+04:21` 这种只能说明两个时间字段打架。

「坐标反查时区是否值得做」不靠感觉，按三个条件同时成立来判断：
已读 EXIF 仍无证据 + 有坐标 + 落在设备时区午夜前后 3 小时内。规则写在 `docs/v3-date-rule.md` §5。

两个计数必须分开，合并就会把结论说反：`fallbackTotal`（只能兜底的张数）与
`fallbackWithLocation`（其中**有坐标**的张数）。真实样本里出现过 4 / 0 的情况，
正确说法是「4 张只能兜底，这 4 张都没有定位」，不是「需要兜底的样本为 0」。

已采 24 张真实照片（两轮读同一批），结论是**暂缓坐标反查**；
但这批样本**不能证明海外日期规则已通过**（没有视频、显式偏移全是 `+08:00`、海外分支没被触发）。

**M11 的落点：归属日在导入时固定。** `dateKey`（`YYYY-MM-DD`）与 `dateSource` 写进媒体，
到访和故事各存一份；展示层全部改读 `dateKey`，不再用 `new Date(...).getDate()` 重推。
否则回国/出差换个时区，那批靠兜底的照片会整体换天。


## 地图聚合

- 判据是**屏幕上两个标记的像素距离**（`CLUSTER_RADIUS_PX = 52`），不是经纬度阈值。
  放大到一定程度自然散开，不需要维护"缩放级别"状态。
- 聚合标记只显示**地点数量**，不叠加到访数——两个数字挨在一起会分不清哪个是地点数。
- 三种时段状态：全部有照片＝实心深色，部分有照片＝强调色描边，全部无照片＝灰色描边并整体变淡
  （变淡走 `Marker` 原生 `opacity`，不触发视图重绘）。
- 点击聚合：能放大就 `animateToRegion` 放大到成员占视口 62% 的位置；放大也分不开
  （坐标几乎重合，或已到 `MIN_REGION_DELTA` 下限）就弹地点列表。
- "放大后能否分开"是用**同一套聚合函数模拟一次**得出的，不是另写一套阈值判断。
- 入场动效只在标记**挂载**时播一次：`key` 由成员构成决定，所以平移地图、切换时间轴
  都不会重新挂载 → 不会重播；只有缩放导致拆开/合并时才会有一次。

## 阅读页的图片尺寸

单张大图按"一屏看全"的偏好来定尺寸（注意：页面本来就能滚动分段看完长图，这里缩小是为了不必滚动）：

- 不依赖 `aspectRatio` 反推高度，直接给显式像素宽高；
- 盒子 = 内容宽 × 屏幕可视高的 52%（`maxReaderMediaHeight`）；
- 图片按 contain 语义等比缩进盒子（`fitWithin`）：横图铺满整宽，竖图缩到盒高以内并水平居中；
- 竖图在小屏上会比原来窄一些、两侧留白，这是预期；
- 半宽格子里的竖图高度由真实宽高比算出，不再用固定的 1.3 倍近似值。

52% 是**原型默认值**，不保证标题多行 + 正文时一定一屏放得下。若真机上仍遮挡，
应改为测量图片上方实际占用、按可用高度计算，而不是反复调这个比例。

> `cover` 是否裁切只取决于容器与原图的宽高比是否一致，与图片元数据是否正确无关——
> 元数据一致只说明比例算得对，不能推出"一定不裁"。

## 整理的约定

- 列表右上角「选择」或长按任意一本进入多选；选中 ≥2 本可合并，选中 ≥1 本可删除。
- 合并标题由 store 自动生成（`地点 · 起止日期`），不弹输入框打断操作；进合集后可在编辑页改。
- 合集 id 用「时间戳 + 自增序号」，只用时间戳会在同毫秒连续合并时撞 id，导致合集指向自己。
- 删除是软删除：`isDeleted = true`，对象、照片、地点都不动；删完自动展开「已删除」区，恢复入口当场可见。
- 拆分必须确认，因为按合并前快照还原，**合并之后在合集里做的修改会丢弃**。
- 合并可以嵌套（合集再与第三本合并），拆分按层还原。

## 编辑页的约定

- 所有修改都走 `appStore` 的语义化 action（`setStoryTitle` / `setStoryCover` /
  `moveStoryMedia` / `setStoryLayout` / `setStoryCoverTitleMode` / `setStoryText` /
  `toggleHighlightedMedia`），页面不直接拼 patch 写 store。
- 校验在 store 层：空标题、不属于本故事的封面、越界的移动一律被拒。
- 文本输入用本地草稿 + 260ms 延迟提交，卸载和「完成」时都会 flush。
- 改动即时保存，没有"保存 / 取消"的歧义。

## 回归时踩到的两条硬约束

- **tab 页里不要叠加 `insets.bottom`。** `BottomTabView` 是 column 布局，tab bar 作为最后一个
  子节点真实占位，内容区高度已经把 tab bar 挖掉了；再用 `useSafeAreaInsets().bottom` 加一次，
  等于把安全区算两遍——表现是底部卡片凭空浮高、操作条底部多一条空白，而且卡片会压住右侧
  时间轴的下段（那一片正是最早的时段）。地图卡片与滑轨、故事页操作条都按这条改过。
- **时间轴松手回调可能早于本次时段的重渲染。** `Gesture.Pan().onEnd` 里的 `runOnJS` 用的是
  当前闭包，那时组件里的 `summaries` 还是上一个时段的派生结果。凡是在手势回调里要用筛选结果，
  都按 tick 自己的 `range` 现算一次，不要读组件里的派生值。

## 已知限制

- 存档是**全量覆盖写**，没有节流。四层一起写之后每次编辑都会重写一遍完整 JSON
  （含全部照片记录）；示例规模无所谓，真实相册导入几千张后要改成只写变动或加 debounce。
- 合并只有一步到位的「合并」，没有二次确认，也没有 undo 栈；误合并要到阅读页拆开。
- 选中地点后没有主动收起底部卡片的入口（点另一个地点或进详情才会变）。
- 聚合半径固定 52px，不随标记疏密自适应；地点重合时只给列表，不做"蜘蛛网"散开。
- 时间轴粒度是**整条统一**的（全部按日 / 按月 / 按年），没有「远处按年、近处按日」的混合刻度；
  按日时最多 31 格，再多就整体跳到按月，中间没有过渡动画。
- 时间轴刻度按**归属日**离散比较之后，跨午夜的到访只算在开始那一天——
  这是刻意的（否则同一批照片会被算两格），但代价是看不到「这次到访延到了第二天」。
- 照片排序用上下箭头，不是拖拽。
- 合集标题只能自动生成，界面上没有让用户直接输入合集名的入口（可进合集后在编辑页改）。
- 拆分按合并前快照还原，合并后在合集里做的修改会丢弃（确认弹窗已说明）。
- 时间轴松手后的地图跟随一次只挑「当前时段到访最多」的一个地点，跨城市时不会一次展示全部。
- 时间轴只认一套像素几何，但**没有真机确认过**：地图页依赖 `react-native-maps`，
  这个库没有 Web 实现，本地连预览都起不来（见 `docs/v6-rail-geometry.md` 第 4 节）。
  断言覆盖的是几何数值，不是渲染结果。
- 轨道高度不足两端内缩（< 32px）时有效高度为 0，拖动不响应，界面上也不给提示。
- 编辑页的键盘避让未在极小屏（SE 尺寸）上验证过。
- 图库多选移除没有「全选」，也没有跨到访的批量操作；一次只能在当前到访里选。
- 移除照片**没有 undo 撤销条**，只能去「已移除的照片」里再点一次恢复。
- 恢复照片时若原故事已被删除，照片会回到数据里但仍不可见（故事不活跃）——
  界面在回收站能恢复，但不会提示「先恢复故事」。
- 地图空状态是一张卡，没有「导入照片」的直接入口（要绕到故事页 → 相册）。
- 大图没有「点开看全屏」，尺寸上限固定为半屏高，短屏设备上竖图会明显变小。
- 标记入场动效依赖 `Marker` 内部视图动画。react-native-maps 是把标记栅格化成图片显示的，
  真机上可能看不到动画（此时会退化成直接出现，不会停在半透明或缩小状态）。
- iPad 分屏未验证：`VisitCardStack` 和到访图库的格子尺寸用的是模块级 `Dimensions` 常量。

真实相册那一侧的限制：

- **缩略图会触发 iCloud 下载。** `Asset.getUri()` 的 `isNetworkAccessAllowed` 是 `true`，
  iCloud 上的资产第一次进列表会真的开始下载原图。现在只靠页大小 24 + 并发 3 + 手动翻页压着，
  导入时也是**逐张顺序读**（并发出错更容易被系统掐掉，顺序还能稳定显示进度）。
- **列表显示的是原尺寸图。** 新版 API 没有缩略图接口，只能把原图 URI 交给 `<Image>` 让它降采样，
  24 张 48MP 的图同时解码仍有内存压力。后续要在原生侧按 `targetSize` 出缩略图。
- **视频没有缩略图**，只给占位卡、类型文字和时长；**导入时直接过滤掉**。不算视频功能已验收。
- **`Query` 没有 count 接口**，界面只显示「已加载 N 张」，不显示总数。
- **Expo Go 里用的是它自己的权限文案**，`app.json` 里配的 `photosPermission` 只在自建构建生效。
- **导入阈值没有实验标定**：80 m 地点半径、4 小时到访切分都是暂定值。
  前者偏保守（同一个商场里两家店会被并成一个地点），后者决定逛一天回来会切成几本。
- **地点名是「未命名地点 N」**，没做逆地理编码。编号按「已有导入地点数量」推，
  删掉中间某个地点之后新地点可能重号。
- **导入没有预览**：点确认之前看不到将生成几个地点、几本故事，只能在结果面板里回看。
- **取消导入不回滚**：中途取消只停在当前这张，已落库的不撤销——
  但重跑会被 `libraryAssetId` 判重，不会产生重复数据。
- **切换时区后，示例数据仍按设备时区分组**：`dateKey` 只覆盖导入的照片，
  示例素材没有这个字段，依旧走本地时区读法。

## 日期口径：已定（M11）

**照片按拍摄地日期分组，不是按当前所在地日期。**

这一条不是显示细节，它决定三样东西跟着哪个日期走：时间轴的刻度边界、列表的「今天 / 昨天 /
10月12日」分组、默认标题 `地点名 · 到访日期`。上一轮这几处都读 `src/utils/datetime.ts`
的本地时区拆分，所以换口径等于换这一层的输入，不是各页各改。

定下来的做法是**在数据里存一个 `dateKey`（`YYYY-MM-DD`），而不是在展示层重新推导**：

| 层 | 落点 |
|---|---|
| 判定 | `resolveShootDate` → `dateKey` + `dateSource`（`exif-offset` / `exif-datetime-original` / `device-tz`） |
| 存储 | `MediaAsset` / `Visit` / `Story` 各存一份，导入时写入后不再变 |
| 展示 | `datetime.ts` 新增 `dayLabelOf` / `weekdayLabelOf` / `partOfDayOf` / `clockLabelOf` / `formatGroupHeaderKey`，有 `dateKey` 就只读它 |

为什么不在展示层推：`device-tz` 兜底依赖"导出那一刻的设备时区"。如果每次渲染都重算，
回国或出差之后**同一批靠兜底的照片会整体换天**——同一张照片昨天看是 9 月 28 日，
今天看变成 9 月 27 日，而照片本身一个字节都没变。存下来就没有这个问题。

代价写清楚：

- 存量数据（示例素材、v1 存档）没有 `dateKey`，仍走设备时区读法，**切换设备时区时会跨日**；
- 导入之后如果用户改了设备时区，新导入的照片会拿到新的兜底日期——
  但**已经导入过的不会跟着变**，这是想要的行为，也意味着同一趟旅行里跨时区前后的两批照片
  可能落在不同规则下（一批是 EXIF 偏移，一批是设备兜底）。
- 「今天 / 昨天」的判定仍拿设备当前时间去比，只是比的对象从"ISO 解读结果"换成了"固定的 `dateKey`"。

**仍然没定的是坐标反查时区**（第 2 条退路）。已采 24 张真实照片的结论是**暂缓**：
4 张只能兜底的照片都没有定位，反查够不着。但这批样本不能证明海外日期规则已通过——
没有视频样本，显式偏移全是 `+08:00`，海外分支一次都没被触发。判定规则见 `docs/v3-date-rule.md` §5。
