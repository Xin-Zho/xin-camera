# 1. 文档目的

本文档是第一阶段可交互原型的统一交接规格。多个 agent
可以按任务分工实现，但必须遵守共同的数据类型、导航约定和验收标准，避免各自开发出无法集成的页面。

**项目目标：** 在 Windows 电脑上使用 React Native + Expo 开发一个可在
iPhone
上预览的原型，验证真实地图、时间轴、地点到访卡片堆叠、杂志式故事相册和基础编辑流程。

**当前阶段不是完整产品。**
第一阶段使用随项目提供的示例数据和示例照片，不连接真实 iPhone
照片库，不实现后台扫描、真实地点反查、云同步或 AI 图片风格转换。

# 2. 产品范围与明确决策

## 2.1 第一阶段必须实现

1.  iPhone
    竖屏布局，苹果原生简约风：白色背景、系统字体、轻量控件、清晰留白。
2.  底部仅有两个主入口：**地图**、**故事相册**。
3.  设置入口位于右上角。
4.  地图使用真实可交互地图，支持平移、缩放、示例地点标记。
5.  地图右侧有半透明竖向时间轴；时间轴支持年份、月份、日期层级的自适应浏览。
6.  地图地点标记支持缩放聚合；放大后显示地点照片缩略图。
7.  同一个地点在地图上只显示一个地点标记；标记代表照片随当前时间范围更新。
8.  点击地点后显示该地点的到访记录卡片堆叠；每张卡片代表一次到访，显示代表照片和时间。
9.  点击到访卡片进入该次到访的照片/视频图库。
10. 故事相册按时间倒序排列，采用杂志封面式卡片。
11. 故事封面根据照片构图，在"照片上叠加标题"和"照片下方留白标题"之间自适应选择。
12. 故事阅读页使用大图、小图交错的杂志式排版。
13. 支持基础编辑：修改标题、封面、照片顺序、重点照片、排版模板；系统负责其余排版。
14. 支持把多本故事合并为一本，也支持拆分恢复。
15. 删除故事只移除故事展示，不删除地点、到访或媒体记录；已删除故事不自动重建。
16. 提供可运行的示例数据，便于不依赖真实照片库测试核心交互。

## 2.2 当前阶段明确不做

-   不请求真实照片库权限。
-   不读取真实 GPS 或相册元数据。
-   不做真实照片自动分类、截图识别或后台扫描。
-   不做账号、自建服务器、云同步。
-   不做 AI 图片重绘、滤镜或风格转换。
-   不把原始媒体复制到应用私有存储。
-   不实现正式备份导出；只在设置页预留简洁入口或说明。
-   不承诺真实 iOS 后台任务行为。
-   不做 Android 适配作为第一阶段验收条件。

# 3. 技术栈建议

-   **语言：** TypeScript。
-   **框架：** React Native + Expo。
-   **项目模板：** Expo Router tabs 模板，方便组织地图、故事和设置页面。
-   **地图：** `react-native-maps`。iOS 原型优先使用 Apple Maps
    provider，避免第一阶段引入付费地图 API。
-   **导航：** Expo Router；底部只显示地图和故事相册两个
    tab，设置从右上角进入。
-   **共享状态：** 建议使用
    Zustand；如果项目启动时已经选用其他简单状态方案，必须统一后再让各
    agent 开发，不能每个页面各自维护一份数据。
-   **本地持久化：**
    原型阶段可以先用内存状态；如果需要验证重启后保留编辑结果，再使用
    AsyncStorage。不要为了原型引入数据库或后端。
-   **时间轴手势：** 优先用 React Native 的 `PanResponder`
    或项目已安装且兼容 Expo 的手势库实现自定义竖向时间轴。不要假定普通
    Slider 能直接满足竖向拖动需求。
-   **图片：** 使用项目内的本地示例图片，避免原型依赖不稳定的远程图片
    URL。
-   **测试设备：** iPhone + Expo Go
    先验证基础原型；如地图或其他原生模块在当前 Expo SDK/Expo Go
    组合中不可用，再评估开发构建。不要一开始就购买开发者账号。

**版本策略：** 使用 `npx create-expo-app@latest` 和 `npx expo install`
选择兼容版本，不要让不同 agent
各自硬编码不同版本。所有依赖只能由集成负责人统一添加到 `package.json`。

# 4. Windows 开发环境与启动

先在 PowerShell 检查：

``` powershell
node -v
npm -v
git --version
code --version
```

如果 Node.js 未安装，安装官方 Node.js LTS
版本后重新打开终端，再执行以上命令。VS Code 和 Git 缺失时再单独安装。

创建项目：

``` powershell
npx create-expo-app@latest memory-atlas --template tabs
cd memory-atlas
npx expo install react-native-maps
npx expo start
```

如果模板或当前 Expo 版本对命令参数有调整，以
`npx create-expo-app --help` 和 Expo
官方文档为准。安装地图后先单独验证地图能否在 iPhone
预览，再继续大量开发。

基本工作流：

1.  Windows 和 iPhone 连接同一个 Wi-Fi。
2.  在项目目录运行 `npx expo start`。
3.  用 iPhone 的 Expo Go 扫描终端/浏览器显示的 QR 码。
4.  先确认基础页面能打开，再逐步集成地图和交互。
5.  如果 Expo Go
    不支持某项所需原生能力，记录具体错误，之后再决定是否使用 EAS
    development build。

# 5. 信息架构与页面

## 5.1 导航

``` text
App
├── 地图（默认首页）
│   ├── 右上角设置入口
│   ├── 右侧半透明时间轴
│   ├── 地点标记 / 聚合标记
│   ├── 地点详情：到访卡片堆叠
│   └── 到访图库：照片与视频
├── 故事相册
│   ├── 故事封面列表（时间倒序）
│   ├── 故事阅读页（杂志排版）
│   └── 故事编辑页
└── 设置
    ├── 原型说明 / 扫描状态占位
    └── 备份功能占位
```

## 5.2 地图首页

-   每次打开地图时，初始视野聚焦最近回忆所在区域。
-   时间轴选择某个时期后，标记、照片缩略图和高亮状态同步更新。
-   当前回忆仍在视野内时不移动地图；切换到远处地点时再平滑移动。
-   时间轴按年份浏览时显示较大时间范围；按月份浏览时显示当月；精确到日期时重点显示当天。
-   远距离拖动时允许快速跨越年份/月；接近有照片的时期时精确定位到有回忆的日期。
-   旧地点可弱化显示，但不能把"当前时间范围内无照片"误显示为地点不存在。
-   地图拖动、缩放必须仍然可用；时间轴手势区域不要遮挡整个地图。

## 5.3 地图标记和聚合

-   低缩放级别：聚合附近地点并显示数量。
-   点击聚合标记：如果放大能有效区分地点，则自动放大；如果仍然拥挤，则展示地点列表。
-   高缩放级别：地点标记显示当前时间范围内该地点最近一次到访的代表照片。
-   代表照片规则：只从当前选中的时间窗口内选取；同一窗口内使用最近一次到访照片。
-   点击单个地点标记：打开该地点的到访卡片堆叠。
-   第一阶段聚合算法可以按地图缩放级别与坐标网格做近似分组；不要为了原型一开始就引入复杂聚类依赖。

### 5.3.1 实现约定（2026-10-25 落地）

-   **判据是屏幕像素距离，不是经纬度阈值**：两个标记在屏幕上小于 52px 就并成一个。
    这样放大到一定程度会自然散开，不需要额外维护"缩放级别"这种状态。
-   字段落在 `src/domain/clustering.ts`：`CLUSTER_RADIUS_PX = 52`、`MIN_REGION_DELTA = 0.004`
    （约 440 米高，是"点击聚合一键放大"的下限）。两者都是原型默认值，真机手感确认后再定。
-   聚合标记显示**地点数量**（不叠加到访数，避免和地点数混淆）。三种时段状态：
    全部有照片＝实心深色，部分有照片＝强调色描边，全部无照片＝灰色描边并整体变淡。
-   判断"放大后能否分开"用的是**同一套聚合函数模拟一次**，而不是另写一套阈值；
    所以坐标几乎重合（例如同一栋楼里的两个地点）时，点击会直接给地点列表。
-   聚合结果只是渲染建议，**不改任何数据**；地图标记仍然基于 `Place`。

## 5.4 地点到访卡片堆叠

-   每张卡片代表一次到访，不是单张照片。
-   当前选中的到访在最前面；其他到访卡片从后方露出少量边缘。
-   卡片显示代表照片、地点名称、日期或时间范围。
-   用户可以水平滑动或点选卡片，切换同一地点不同时间的到访。
-   点击卡片进入该次到访图库。
-   到访图库按拍摄时间排序，照片和视频均可用示例素材表示。
-   原型阶段不实现真实视频播放也可以，但必须有视频素材的视觉区分和基本点击反馈。

## 5.5 故事相册与阅读页

-   故事粒度为**一次到访一本**（详见 7.2），同一地点的多次到访会呈现为多本。
-   故事列表按开始日期倒序，最新故事在前。
-   使用封面式卡片，封面图片为主，地点和日期作为辅助信息。
-   封面标题布局根据图片构图自适应：标题叠加在照片上，或在照片下方留白区域展示。
-   阅读页使用大图、小图交错的杂志式布局，不要求第一版支持任意拖拽排版。
-   文字以照片为主：自动数据只生成标题、地点、日期；不自动编写照片说明或长篇故事。用户可以自行添加文字。
-   编辑操作包括：修改标题、选择封面、调整照片顺序、标记重点照片、选择有限数量的排版模板。
-   所有编辑动作应立即更新当前 UI；原型可先保存在内存中。

## 5.6 合并、拆分和删除

-   用户选择多个故事后，可以合并成一本故事。
-   合并后，原故事不再单独显示，但底层地点和到访记录仍存在。
-   合并必须可逆：拆分时恢复合并前的故事分组，或允许用户选择拆分位置。
-   删除故事只改变故事展示状态，不删除地点、到访和照片数据。
-   已删除故事不自动重建。原型可以提供"撤销删除"或恢复入口；如果没有恢复
    UI，至少保留数据层状态。
-   不要把"删除故事"实现成删除它引用的照片或地点。

# 7. 核心数据模型（所有 agent 必须共用）

以下是建议的 TypeScript
起始模型。可以按实现微调，但需要由集成负责人统一维护，不能让各 agent
各自定义同名但不兼容的类型。

``` ts
export type MediaKind = "photo" | "video";

export interface MediaAsset {
  id: string;
  uri: string;             // 原型阶段为本地示例图片路径
  kind: MediaKind;
  capturedAt: string;      // ISO 8601
  placeId?: string;
  visitId?: string;
  isScreenshot?: boolean;
}

export interface GeoPoint {
  latitude: number;
  longitude: number;
}

export interface Place {
  id: string;
  name: string;
  coordinate: GeoPoint;
  category?: string;
  mediaIds: string[];
  visitIds: string[];
}

export interface Visit {
  id: string;
  placeId: string;
  startAt: string;
  endAt: string;
  mediaIds: string[];
  coverMediaId: string;
}

export type StoryLayout = "editorial" | "large-cover" | "grid";

export interface Story {
  id: string;
  title: string;
  placeIds: string[];
  visitIds: string[];
  mediaIds: string[];      // 已排序的媒体 ID
  coverMediaId: string;
  startAt: string;
  endAt: string;
  layout: StoryLayout;
  highlightedMediaIds: string[];
  userText?: string;
  isDeleted: boolean;
  mergedFromStoryIds?: string[];
  mergeSnapshot?: Story[]; // 原型中用于可逆拆分；正式版可改为独立快照结构
  updatedAt: string;
}
```

## 7.1 数据关系规则

-   `MediaAsset` 是媒体元数据引用；不复制媒体文件。
-   `Place` 表示一个地理地点；一个地点可有多次 `Visit`。
-   `Visit` 表示某次到访；一条到访包含多张照片/视频。
-   `Story` 是可编辑作品，可以引用一个或多个地点、到访和媒体。
-   自动生成的故事与 `Visit` 默认为 1:1（见 7.2）；只有用户主动合并后，
    一本故事的 `visitIds` 才会多于一条。
-   地图标记基于 `Place`，不是基于 `Story`。
-   删除故事只设置 `isDeleted = true`
    或将它移出活动列表，不删除其引用的地点、到访或媒体。
-   合并故事要保存足够的原分组信息，确保拆分可以恢复。
-   故事媒体顺序独立保存，不能通过修改原始 `Visit.mediaIds`
    来实现故事内排序。

## 7.2 已定案的生成规则：一次到访 = 一本故事

**决定（2026-10-25）：不按地点聚合故事，每次到访各自生成一本。**
同一地点去过三次，故事相册里就是三本独立故事。

原型必须严格按以下规则生成故事：

1.  一个 `Visit` 自动对应一本 `Story`，默认 1:1。`story.visitIds = [visit.id]`，
    `story.placeIds = [visit.placeId]`。
2.  `story.mediaIds` 取该次到访的媒体并按 `capturedAt` 升序排；`coverMediaId`
    默认用 `visit.coverMediaId`，用户可改。
3.  `story.startAt / endAt` 取该次到访的实际起止时间，展示粒度到天。
4.  默认标题为 `地点名称 · 到访日期`（如「海边栈道 · 10月12日」）。同一天同一地点
    有多本时，用时段或序号区分（如「海边栈道 · 10月12日 傍晚」）。标题可编辑。
5.  地图上**仍然是每个 Place 一个标记**，这条不因故事粒度改变而改变。故事粒度
    只影响故事相册，不影响地图层。
6.  因为故事会碎，**合并是这个模型下主要的整理手段**：把同一地点不同到访的多本
    合成一本，或把跨地点的一次出行合成一本。合并后的故事 `visitIds` 可以有多条，
    此时它是一本合集，不再代表单次到访。
7.  合并必须可逆：`mergedFromStoryIds` + `mergeSnapshot` 保留原分组，拆回后仍是
    各自到访对应的那些故事。
8.  故事列表默认按 `startAt` 倒序；同一天的多本按到访开始时间倒序。
9.  不允许为了"看起来整齐"而把同地点的多本悄悄合并——自动重建/自动合并属越权。

## 7.3 尚未最终定案的规则

以下事项不要阻塞原型开发，应先用配置项或固定示例数据实现，并记录为待验证：

1.  同一地点的两次到访，初始考虑以约 4
    小时时间间隔作为分界，但阈值尚未最终确认。（该阈值只决定"切成几本"，不影响
    7.2 的"一次到访一本"结论。）
2.  聚合标记的精确像素阈值和时间轴手势灵敏度，需要在 iPhone
    上测试后调整。（当前暂定：聚合半径 52px，点击放大下限 latitudeDelta 0.004，
    见 5.3.1。真机上手感不对就改这两个常量，不要散落在页面里。）
3.  真实地点名称解析、GPS 容差和无 GPS 照片的正式处理规则属于第二阶段。

原型应使用固定 mock 数据演示预期体验，不要假装这些自动识别规则已经实现。

# 8. 状态管理与跨页面接口

建议由一个共享 store
管理数据，避免地图页和故事页各自维护互不一致的副本。

建议 store 暴露下列操作（命名可调整，但含义需保持一致）：

``` ts
interface AppActions {
  setSelectedTimeRange(range: TimeRange): void;
  selectPlace(placeId: string): void;
  selectVisit(visitId: string): void;
  updateStory(storyId: string, patch: Partial<Story>): void;
  reorderStoryMedia(storyId: string, orderedMediaIds: string[]): void;
  mergeStories(storyIds: string[], title: string): string;
  splitStory(storyId: string): string[];
  deleteStory(storyId: string): void;
  restoreStory(storyId: string): void;
}
```

`TimeRange` 可以定义为：

``` ts
export type TimeGranularity = "year" | "month" | "day";

export interface TimeRange {
  startAt: string;
  endAt: string;
  granularity: TimeGranularity;
}
```

页面间只传递 ID，不要把整份故事对象塞进路由参数。详情页根据 ID 从 store
读取当前数据。

原型阶段的故事由 `src/data/mockStories.ts` 直接提供，**不要求实现自动生成逻辑**，
但 mock 里的故事必须符合 7.2 的「一次到访一本」规则：一本故事的 `visitIds`
只有一条（合并产生的合集除外），标题按「地点名 · 到访日期」格式。
后续接入真实数据时，生成动作建议命名为 `createStoryFromVisit(visitId)` 并复用同一规则。

# 9. 时间轴行为细节

-   时间轴是右侧悬浮的半透明竖向控件，不是独立页面。
-   显示当前选择的年份/月/日，以及少量上下文刻度。
-   拖动时更新 `TimeRange`；地图标记和代表照片据此计算。
-   远距离浏览以年份/月为单位快速移动；接近有媒体的日期后，允许更精细的日期定位。
-   如果选中时间范围内某地点没有媒体，该地点不应显示为当前时期的活跃照片标记；可以弱化历史标记，但需有统一规则。
-   地图移动采用"智能跟随"：目标在视野内则不动，目标在视野外才平滑移动。
-   时间轴拖动过程中避免每个像素都触发地图动画；可在拖动期间更新预览，必要时在松手或跨越较大距离后执行地图动画。
-   地图拖动与时间轴拖动要分离手势区域，避免互相抢事件。

# 10. 视觉设计系统

整体采用苹果原生简约风；故事内容保留杂志式排版。

建议基础 token：

-   背景：白色或接近白色。
-   主文字：近黑色。
-   次级文字：中性灰。
-   分隔线：浅灰。
-   圆角：统一、克制；避免所有元素都做成大圆角卡片。
-   阴影：少量用于悬浮时间轴和到访堆叠。
-   字体：优先使用 iOS 系统字体。
-   动效：短、平滑、不夸张；地图平移和卡片切换不应抢注意力。
-   安全区：所有页面适配 iPhone 刘海、动态岛和底部 Home Indicator。
-   可触控区域：主要按钮尽量达到约 44×44 pt。
-   不在地图上堆叠过多文字；地点名和日期优先放在卡片中。

故事封面采用自适应布局： 1.
如果照片有适合叠字的留白或对比度，标题可叠在照片上。 2.
如果照片主体复杂或文字不易辨认，标题放在图片下方。 3.
不能只根据照片方向判断；原型可用简单规则或预设 `coverTitleMode`
模拟，不要求第一阶段做 AI 构图分析。

-   [ ] 地图可缩放、平移。
-   [ ] 右侧半透明时间轴可拖动。

-   [ ] 同一地点的不同到访可切换。

-   [ ] 最新故事在前。
-   [ ] 同一地点的每次到访各自生成一本故事（三次到访 = 三本，不按地点自动合并）。
-   [ ] 默认标题为「地点名 · 到访日期」，且可编辑。
-   [ ] 同地点多本合并成一本后，拆分能还原成各自到访对应的故事。

-   [ ] 合并后的故事可以拆分恢复。
-   [ ] 删除故事不删除底层地点、到访和媒体。

-   [ ] 原型不请求真实照片库权限。

-   [ ] 未实现的真实照片扫描、备份和 AI 功能明确标记为"后续版本"。

# 13. 建议开发顺序

1.  **先让空项目在 iPhone 上运行。**
2.  建立共同类型、mock 数据和 store。
3.  完成双 tab 导航与设置入口。

# 14. 第二阶段（本文件不要求实现）

后续可以规划： - 使用 iOS 照片库 API 读取相机照片和视频。 -
