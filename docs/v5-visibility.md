# M12 照片可见性：一套判定，四个消费者

> 起因：删除故事之后，故事列表里那本没了，**照片却还在地图标记、到访图库和时间轴上**。
> 地图那侧按"到访存在"计数，故事那侧按"故事没删"过滤，两边各答一次同一个问题，答案必然分叉。

这一轮只做一件事：把「这张照片还该不该显示」收成一个函数，让所有地方都问它。

---

## 1 判定（`src/domain/visibility.ts`）

判定顺序不可交换：

| 顺序 | 条件 | 结果 | 隐藏原因 |
|---|---|---|---|
| 1 | `media.removedAt` 有值 | 隐藏 | `removed` |
| 2 | 被至少一本**活跃故事**引用 | 显示 | — |
| 3 | 引用它的故事都删了 / 都并走了 | 隐藏 | `story-deleted` |
| 4 | 没有任何故事引用 | 隐藏 | `unlinked` |

**活跃故事** = `!isDeleted && !mergedIntoStoryId`。

几个刻意的选择：

- **移除优先于一切**。用户明确从图库移除了这张，就算故事还活着也不显示。反过来（故事优先）
  会让"移除"这个动作在某些情况下看起来没生效，用户只能反复点。
- **被合并掉的源故事不活跃，但它的照片照样显示**——合集引用着它们。判定看的是"有没有活跃故事引用"，
  不是"它原来属于哪一本"。所以合并/拆分不需要任何额外处理。
- **`unlinked` 也隐藏**。没有故事承载的照片，点开也看不到任何上下文；让它出现在地图或图库上，
  用户找不到"这是哪次旅行的"。宁可少显示一张，也不给一个没有归属的格子。
- **媒体不存在同样不可见**（`stateOf` 里查不到就算 false）。存档被手改过、导入中断都可能留下这种 id。

返回结构里 `counts` 分四项（total / visible / removed / storyDeleted / unlinked），
不是为了统计好看，而是因为界面要能说清"为什么这张不见了"——三种原因的恢复动作完全不同。

---

## 2 为什么只写 `removedAt`，不删引用

移除照片时**不动** `story.mediaIds` / `visit.mediaIds` / `place.mediaIds`，只给媒体打一个时间戳。

理由三条：

1. **恢复要能原样回来。** 顺序、封面位置、精选标记全挂在 `story.mediaIds` 的顺序和
   `coverMediaId` 上。删引用等于把这些一起丢了，恢复出来就是一张乱序的照片。
2. **一个开关就够。** 多存一处状态（比如 `story.mediaIds` 里也去掉），就多一处可能对不上的地方。
   数据里两处表达同一件事，迟早会有一处忘了改。
3. **存时刻而不是布尔值**，回收站才能按"最近移除"排序。

代价是「地点媒体数」「到访张数」这些聚合字段会包含已移除的照片。这些数字全部改成经
`visibleCount` 计算，不再直接读 `mediaIds.length`。

### 封面被移除

`story.coverMediaId` 可能指向一张已移除的照片。两种处理都错：

- 显示灰块 → 用户以为是加载失败；
- 顺手改掉 `coverMediaId` → 用户恢复那张之后，封面悄悄变成了另一张。

所以只在**读取时回退**（`pickVisibleCover`）：原封面可见就用它，否则用第一张可见照片，都没有就返回
`undefined` 由界面说清楚。字段永远不动。

编辑页也是同一套：`effectiveCoverId` 用回退结果，否则编辑页的「封面」标记和阅读页显示的照片会不一致。

## 3 联动（都不需要额外代码，判定变了结果就变了）

| 操作 | 结果 |
|---|---|
| 删除故事 | 软删；它**独占**的照片变 `story-deleted` → 到访没有可见照片 → 地图标记消失、时间轴收缩；被其他故事共用的照片照常显示 |
| 恢复故事 | 照片重新可见 → 地图标记与时间轴范围一起回来 |
| 从图库移除照片 | 打 `removedAt` → 该照片从地图、图库、阅读页、时间轴消失 |
| 恢复照片 | 抹掉 `removedAt` → 回到原位置 |
| 地点已无可见照片 | `selectMapPlaceSummaries` 不返回它 → 标记隐藏。数据没删，地点页仍可进 |
| 全部内容已删除 | 时间轴无刻度、地图显示空状态卡片；**不回退示例数据** |

最后一条值得单独说：`merge` 里那条"故事一条都留不下就回退示例数据"的规则，判断的是**存档损坏**，
不是**用户删空了**。软删除的故事仍然在 `stories` 数组里，所以正常删空不会触发它。
如果真的触发了，说明存档结构坏了，那时回退示例数据是对的。

### 地图的两个过滤层次

`selectPlaceSummaries` 保留旧语义：**窗口内没有照片的地点仍然返回**，由地图弱化显示。
"这一格暂时没内容"和"这个地点不该出现"是两件事，混成一个函数会两边都不好用。

`selectMapPlaceSummaries` 在它之上加两道：

1. `unlocated` 的地点不返回（没有坐标，画出来会落在几内亚湾）；
2. `coverMedia === undefined` 的地点不返回（一张可见照片都没有）。

第 2 条就是「删故事后地图标记消失」的落点。

## 4 移除与恢复的入口

### 图库（`visit/[visitId].tsx`）

右上角「选择」或**长按任意照片**进入选择模式 → 多选 → 底部「从回忆相册移除 N 张」。

确认弹窗的正文固定写明：

> 这 N 张会从地图、到访图库和时间轴隐藏。iPhone 系统相册里的原图不会被删除，之后随时可以恢复。

图库底部有「已移除 N 张 · 查看」区，展开后缩略图降透明度 + 「恢复」按钮。移除完成后自动展开，
让恢复入口当场可见——否则这个动作等于不可撤销。

### 回收站（`app/removed.tsx`）

设置 → 回忆相册 →「已移除的照片」，按 `removedAt` 倒序，支持逐张和全部恢复。

**为什么不能只靠图库那一处**：某次到访的照片全部被移除后，`isVisitVisible` 为 false，
那张到访卡片就从地点页消失了——用户再也进不去那个图库，恢复入口跟着一起被藏掉。
回收站不看到访归属，任何一张都能从这里恢复。

## 5 时间轴：跟随有效照片

刻度范围不再从到访取最早/最晚，也不再被示例数据的跨度撑住。输入只有一样：
**当前有效照片的归属日**。

```
validMedia → computeMediaSpan → buildTimelineTicks
```

| 跨度 | 粒度 | 标签 |
|---|---|---|
| ≤ 31 天（`DAY_GRANULARITY_MAX_DAYS`） | `day` | `10月12日` |
| ≤ 24 个月（`MONTH_GRANULARITY_MAX_MONTHS`） | `month` | `10月`；跨年时 1 月那格显示 `2026` |
| 更长 | `year` | `2026` |

固定按月不行：只有一天照片时，一天的回忆会占满整条滑轨，拖动完全没有手感。

### 范围与归属日用同一套口径

`rangeKeyOf(range)` 把 `TimeRange` 折算成粒度键（`YYYY-MM-DD` / `YYYY-MM` / `YYYY`），
`isDayKeyInRange(dayKey, range)` 做离散比较。

旧实现是"时刻区间求交"（`visitOverlapsRange`），问题在于：

- 一个 10-31 23:00 → 11-01 01:00 的到访会**同时**出现在 10 月和 11 月两格；
- 照片的归属日是拍摄地日（`dateKey`），而 range 边界是设备时区构造的，两者本来就不是一套。

现在照片属于 `2026-10-12`，就只属于 10 月 12 日那一格。代价见「已知限制」。

### 收敛（`reconcileRangeToSpan`）

在**所有会改变可见集合**的 action 里调用一次：`deleteStory` / `restoreStory` /
`removeMedia` / `restoreMedia` / `importLibraryAssets`。

落点是"离原选中位置最近的刻度"：

- 删掉最新一批 → 当前选中超出上界 → 落到新的最晚一格；
- 删掉最早一批 → 还在范围内 → 原地不动；
- 粒度从月降到日（只剩一天照片）→ 收敛到那一天。

已经落在刻度上时**原样返回同一个对象引用**，避免一次无意义的全局通知。

`reconcileRangeToSpan` 不处理空跨度：`span` 为 `null` 时 store 保留原值，页面显示空状态。
在这里编一个假范围糊弄过去，会让空状态永远出不来。

## 6 重复导入不会让已移除的照片复活

去重键仍是 `libraryAssetId`，而 `media` 记录一直在（只是多了 `removedAt`）。
`planLibraryImport` 的 `existingAssetIds` 只看 id 存不存在，所以：

- 重新导入同一张 → `skippedDuplicates + 1`，`removedAt` 保持不动；
- 不会生成第二份副本（断言 9.4–9.8 覆盖）。

恢复只有两条路：图库底部的已移除区、回收站。导入不是第三条。

## 6b 移空自动删除（真机验收后新增的产品逻辑）

用户确认的规则：**故事里的照片被全部移除后，故事也跟着进「已删除」**——
不然故事列表里会留下一批「照片已隐藏」的空壳卡片。

实现在 store 动作里，不在判定层（判定层刻意不改数据）：

- `removeMedia`：写入 `removedAt` 之后，检查所有活跃故事——
  本来有照片（`mediaIds.length > 0`）、现在一张可见的都不剩 →
  软删除并打 `Story.deletedByEmptying = true` 标记。
  天生没照片的不碰；只删「本来有、被移空」的。
- `restoreMedia`：对称恢复——带标记的故事只要有照片重新可见就自动回来
  （`isDeleted: false` + 清标记）。可见性判据用「候选故事暂时算活跃」的探针快照，
  否则自家照片全被算成 `story-deleted`，故事永远活不过来。
- `deleteStory` / `restoreStory`（手动）：一律清标记。
  手动删除是最终决定，之后恢复照片不复活（断言 11.9–11.10）；
  手动恢复后照片再被移空，重新走自动删除链（断言 11.11）。

故事页「已删除」区对这类故事单独说人话：「照片已全部移除，恢复照片即可恢复这本」——
它的照片 hide reason 是 `removed` 不是 `story-deleted`，旧文案会说成"照片仍被其他故事使用"。

## 7 验证记录

新增 `test-visibility` 121 条（108 + 移空自动删除 13 条），覆盖：

- **判定**：四类原因的每条分支、移除优先于故事引用、无主照片不外露、被合并掉的源故事其照片仍可见、
  不存在的 id、入参不被修改、三种原因文案互不相同、`dateKey` 优先于设备时区；
- **封面与计数**：封面可见就用、封面被移除则回退、全部不可见返回 undefined、`visibleCount` 只算可见、
  到访全移除即不显示；
- **跨度**：空 / 单天 / 31 天 / 32 天 / 24 个月 / 25 个月六个边界、`dateKey` 让同一时刻只算一天、
  示例数据的跨度是 2026-02-11 ~ 2026-10-12（被删故事那张不再撑范围）；
- **刻度**：日刻度的数量与首尾、每格范围与 key 自洽、跨年时 1 月那格显示年份、年刻度逐格年份；
- **落窗**：日/月/年三档的匹配与不匹配、跨午夜到访只算开始日、带 `dateKey` 的到访按固定归属日判；
- **收敛**：已在刻度上返回原对象、超上界、超下界、月→日、日→月；
- **store 联动**：删故事后独占照片隐藏而共用照片仍在、媒体本身没被删、窗口收回、
  恢复后照片与范围一起回来、移除/恢复的幂等（空操作不写 store）、
  全部删完时可见为 0 但媒体数量不变、地图一个标记都不剩；
- **地图**：被删故事的地点不出现、其余都在、每格都有可见封面、未定位不上地图、
  封面被移除时回退、`selectPlaceSummaries` 仍返回地点但计数为 0；
- **导入**：移除后重新导入被跳过且不复活、没有副本、只能从恢复入口回来；
- **存档**：`removedAt` 随媒体一起进存档、四层齐全。

合计 **701 条**（91 状态机 + 31 v1 兼容 + 38 存档 + 84 相册 + 154 日期 + 122 导入规划 +
73 导入落库 + 108 可见性），`tsc --noEmit` 零错误，`expo export --platform web` 退出码 0。

跑断言的过程里抓到两个真 bug：

1. `VisitCardStack` 的 `active` 索引在到访列表变短后可能越界（移除照片后卡片堆整个空掉）——
   现在读的时候夹一次 `Math.min(activeRaw, visits.length - 1)`。
2. 编辑页的「封面」标记读的是 `story.coverMediaId`，而阅读页读的是回退结果。
   封面被移除后两处指着不同的照片。统一走 `effectiveCoverId`。

## 8 已知限制

- 时间轴粒度**整条统一**，没有「远处按年、近处按日」的混合刻度；按日最多 31 格，再多就整体跳到按月。
- 跨午夜的到访只算开始日（离散比较的直接后果），看不到"延到第二天"。
- 图库没有「全选」，也不能跨到访批量移除。
- 移除没有 undo 撤销条，只能去回收站再点一次恢复。
- 恢复照片时若原故事已被删除，照片回到数据里但仍不可见（故事不活跃）——回收站不提示"先恢复故事"。
- 地图空状态是一张卡，没有「导入照片」的直接入口。
- 80 m 地点半径与 4 小时到访切分仍**没有实验标定**（与本轮无关，但会同时影响可见性的观感：
  地点切碎之后，删一本故事只会让地图上少一个小标记，而不是消失一片）。
