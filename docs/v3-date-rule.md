# 日期口径验证（v3）

- 对应提交：见仓库 `git log`（本文件与实现同一笔提交）
- 范围：**只验证「照片归到哪一天」的规则**。不生成到访、不生成故事、不写 store。
- 目标口径：**旅行照片回到国内后，仍归在拍摄当地那一天。**

## 1 问题拆成两半

| 问题 | 谁回答 | 状态 |
|---|---|---|
| 「这张照片是什么时刻拍的」 | `Asset.creationTime`（Unix 时间戳，绝对时刻） | 上一轮已验证：单位注释写秒、iOS 实现是毫秒，按量级判定 |
| 「这个时刻在拍摄地属于哪一天」 | 需要**拍摄地的 UTC 偏移** | 本轮验证 |

相册 API **没有**「拍摄地时区」这个一等公民字段（`getLocation()` 只给经纬度，封装层连
`CLLocation.timestamp` 都没取）。所以偏移只能从 EXIF 里找，找不到就退回设备时区。

## 2 三个来源，按可靠性排序

| 顺序 | 来源 | 依据 | 缺失时的样子 |
|---|---|---|---|
| 1 | `exif-offset` | EXIF `OffsetTimeOriginal` / `OffsetTimeDigitized` / `OffsetTime` / `TimeZoneOffset`，叠加在 `creationTime` 上 | 截图、社交软件保存的图基本没有 |
| 2 | `exif-datetime-original` | EXIF `DateTimeOriginal` 是**相机写的当地墙上时间**，日期部分本身就是拍摄地日期 | 同上；被编辑/导出过的图可能被改写 |
| 3 | `device-tz` | 都没有 → 回退设备时区，界面明确标成「设备时区」并提示会错一天 | — |

**顺序 1→2 不是随便排的**：声明的偏移是显式数据，DateTimeOriginal 是墙上时间（没有偏移含义），
后者更接近「人眼看到的日期」但无法还原精确时刻，所以有偏移时优先用偏移算日。

### 2.1 反推偏移：本轮新增的判据

`DateTimeOriginal`（墙上时间）和 `creationTime`（绝对时刻）相减，得到的就是**推定偏移**：

```
impliedOffset = wallClockAsUtcMs(DateTimeOriginal) - creationTime
```

这个值有三重用途：

1. 没有 `OffsetTimeOriginal` 的图，用它当等效偏移（算出午夜距离、显示）；
2. **验证 `creationTime` 本身有没有被规范化**。如果一张明显的海外照片，反推偏移等于设备偏移，
   说明系统在落库时按设备时区解释了墙上时间——这是一个必须知道的坏消息；
3. 反推值不落在 ±14h 或不是 15 分钟粒度时，判定为不可信，改为退回绝对时刻。

界面会把「反推偏移 / 是否合理 / 是否等于设备偏移」三件事都显示出来。

## 3 判定流程

```
epochMs 拿不到                              → source=none，日期为空，不猜
EXIF 有可用偏移                             → 日期 = dateKeyFrom(epochMs, 偏移)
EXIF 有 DateTimeOriginal 且反推偏移合理      → 日期 = DateTimeOriginal 的日期部分
其余（未读 / 无时间字段 / 反推不合理）        → 日期 = dateKeyFrom(epochMs, 设备偏移)，source=device-tz
```

补充规则：

- 偏移算出日和墙上时间日不一致 → 标记 `conflict`，按偏移取，并把两条证据都列出来；
- 一律同时算出 `deviceDateKey`，两者不同就标记**跨日**——跨日的样本就是「旧规则会错」的样本；
- 任何一个候选来源的可用性都写进 `evidence`，界面逐行显示，不只给结论。

## 4 这一轮要采的样本（5 类）

样本不用多，但每类都要有，否则结论没有外部效度。

| 类别 | 怎么找 | 要看什么 |
|---|---|---|
| 普通本地照片 | 相机原图、国内拍摄 | 归属日应等于设备口径，**不该被规则改动** |
| 海外旅行（非午夜） | 拍摄地时区 ≠ +08:00，当地白天 | `source` 应为 EXIF 之一，跨日为 0 |
| 海外旅行（当地午夜前后） | 当地 21:00–03:00 | **最关键**：跨日必须为 1，否则规则没生效 |
| 截图 / 社交软件保存 | `subtypes` 含 `screenshot`，或文件名形如 `mmexport*` | 预期没有 EXIF 时间 → 走设备时区，看这条兜底是否可接受 |
| 视频 | `mediaType=video` | 视频有没有 EXIF、创建时间是否可靠 |

操作：相册页 →「日期口径验证」→ 顶部筛选切到对应类别 → 逐张点「读 EXIF」。
不点就不读——`getExif()` 在 iOS 上会把当前版本导出成临时文件，iCloud 资产还会触发下载。

**每一行要记录的事实**（页面上一行就是一条记录，右上「分享汇总」可整段导出去）：

- 归属日 + 来源
- 设备时区口径的日期、是否跨日
- `creationTime` 原值 / UTC 时刻 / 设备本地时刻 / 生效偏移
- 定位有无
- EXIF：时间字段个数、偏移字段路径、`DateTimeOriginal` 原文
- 反推偏移、是否合理、是否等于设备偏移

## 5 「坐标反查时区」值不值得做——先定判定规则

不先定规则，等看到数据就会变成「感觉有必要」。判定只看三个条件同时成立：

```
已读 EXIF（不是没读） & 拿不到时间证据 & 有坐标 & 落在设备时区午夜前后 3 小时内
```

页面按这个算出一个数 `fallbackNearMidnightWithLocation`，并给出四档结论：

| 条件 | 结论 | 含义 |
|---|---|---|
| EXIF 一张都没读 | `need-data` | 现在下结论等于猜 |
| 需兜底且有坐标 = 0 | `no-need` | 反查不值得做：能读到证据的都有证据，读不到的也没坐标 |
| 有坐标但不在午夜前后 | `low` | 日粒度基本不受影响，等真出现这类样本再说 |
| 有坐标且在午夜前后 | `worth` | 建议**只对这类样本**反查，而不是全量接入离线时区边界数据 |

## 6 明确不做的事

- 不引入离线时区边界数据（几十 KB 到几 MB，取决于精度），等第 5 节的结论；
- 不把 `device-tz` 兜底结果伪装成准确值——来源单独一个枚举值，界面上是橙色标签；
- 不按「当前所在地日期」分组，这一轮只验证「拍摄地日期」这条路能不能走通；
- 不改时间轴、列表分组、默认标题这三处消费方。口径定案后才动它们。

## 8 视频的当前定位

**「能识别，尚未提供预览」，不等于视频功能已验收。**

列表里的视频现在是一张明确的占位卡（深底 + 播放图标 + 「视频」文字），有 `duration` 时右下角带时长。
之前只有图标没有文字、且和「照片无法预览」的浅灰占位长得很像，容易被当成加载失败，本轮改掉了。
视频缩略图要 AVAsset 抽帧，不在这一轮范围内。
