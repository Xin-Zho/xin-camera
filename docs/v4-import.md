# 照片导入（v4）：从相册到地点 / 到访 / 故事

这一轮把只读实验接进了主流程：相册里的照片能变成地图上的地点、时间轴上的到访、列表里的故事。
规则层在 `src/library/importPlan.ts`（纯函数），落库在 `appStore.importLibraryAssets`，
入口是「相册 → 导入」。

**导入是不可撤销的写入。** 生成一批错的地点或到访，用户只能一条条删。所以规则全部先在纯函数里
算完，再一次性落库——这样这套判断能脱离真机、在 Node 里跑断言（见 §8）。

## 1 四条硬规则

| # | 规则 | 为什么 |
|---|---|---|
| 1 | 有定位 → 同一片区域合成一个地点；没定位 → 全部收进「未定位」一处 | 照片不能因为没坐标就丢，也不能被画到几内亚湾 |
| 2 | 同一天 + 同一地点 + 间隔 ≤ 4 小时 = 一次到访 | 一次出行一本，不是一张照片一本 |
| 3 | 重复导入不重复生成 | 以 `libraryAssetId` 为数据源键 |
| 4 | 不覆盖用户已有编辑 | 用户改过的故事不追加，另起一本 |

## 2 归属日在导入时固定

这是本轮**最重要的结构性决定**，也是最容易被当成细节跳过的一条。

问题：日期的三个来源里，`device-tz` 兜底是「导出那一刻的设备时区」。如果展示层每次都用
`new Date(capturedAt).getDate()` 重新推日期，那么回国、出差、跨时区飞行之后，
**那批靠兜底的照片会整体换天**——同一批照片，昨天看是 9 月 28 日，今天看变成 9 月 27 日。

做法：

- `resolveShootDate` 在导入时算出 `dateKey`（`YYYY-MM-DD`）与 `dateSource`，**写进媒体**；
- 到访和故事也各存一份 `dateKey`；
- 展示层新增一整套 `dateKey` 感知函数（`dayLabelOf` / `weekdayLabelOf` / `partOfDayOf` /
  `clockLabelOf` / `formatGroupHeaderKey`），有 `dateKey` 就只读它，**不再经设备时区解读**；
- 只有没有 `dateKey` 的老数据（v1 存档、示例数据）才退回旧的本地时区读法。

`formatClockLiteral` 单独存在，是因为「读 ISO 字面量里的时分」和「按设备时区解读 ISO」是两件事：
前者用来显示照片当地的时刻，后者会把 `10:44+08:00` 在 UTC-8 的设备上显示成 `18:44`。

一句话：**日期在导入那一刻钉死，之后谁也不许重算。**

## 3 地点规则

- **半径 80 m**（`PLACE_RADIUS_METERS`）。约一个街区——比地图聚合半径宽，但不会把两个商场并成一个。
  逐个候选点找最近的、在半径内的、非「未定位」的已有导入地点，找不到就新建。
- **只和导入产生的数据合并**（`origin === 'library'`）。示例地点永远不参与，
  否则真实照片会跑进示例相册里。
- **未定位单独一处**，固定 id `p-lib-unlocated` + 固定名「未定位」，多次导入都落到同一处。
  它带 `unlocated: true`，地图标记、时间轴、初始视野全部过滤掉它。
  坐标写 `0,0` 只是为了满足类型，不会被画出来。
- **未定位不参与距离匹配**：几内亚湾附近拍的照片（坐标真的接近 `0,0`）不会被并进「未定位」。
- 新地点默认名按已有数量编号（`未命名地点 N`），跳过未定位那一处。
- 地点 id 用经纬度（5 位小数）的 FNV-1a 短哈希，**同一坐标在两台设备上得到同一个 id**。

## 4 一次到访怎么切

宿主到访必须同时满足四个条件：

```
同 placeId & 同 dateKey & 间隔 ≤ 4 小时 & 故事没被用户改过（或本次新建的）
```

4 小时是**暂定阈值**（`VISIT_GAP_MINUTES = 240`），它只决定「切成几本」，不影响
「一次到访一本」这条结论。没有做实验标定，所以写在这里而不是藏进代码常量。

`dateKey` 优先于间隔：23:30 和次日 00:30 只差 1 小时，但归属日不同，**必然切成两本**。
反过来，跨归属日合并是绝对不允许的——那会让最后一张照片的日期和标题对不上。

第二本起，标题自动加当地时刻后缀：`未命名地点 1 · 9月28日 · 15:44`。
没有后缀的两本标题完全一样，列表里分不清。判断「今天这个地点是不是已有故事」时会跳过
已删除和已合并的故事——否则用户删掉之后再导入，会莫名其妙得到一个带时刻后缀的标题。

## 5 重复导入与「不覆盖用户编辑」

**去重键是 `libraryAssetId`**（PHAsset id）。导入过的一律跳过，同一批里重复出现的也只算一次。
一行新照片都没有时**完全不写 store**：不刷订阅者，也不搅动 `timeRange`。

**追加只在故事没被用户改过时发生。** 三种情况会另起一本：

| 故事状态 | 行为 | 理由 |
|---|---|---|
| `editedByUser === true` | 新建故事 | 追加会打乱用户排好的封面和顺序 |
| `isDeleted` | 新建故事 | 删了就是不想看了，别往里塞 |
| `mergedIntoStoryId` 有值 | 新建故事 | 合集是用户手动组的，追加会让合集内容莫名变多 |
| 孤儿到访（故事已不存在） | 新建故事 | 照片追加进去就没有故事承载，用户在列表里找不到它 |

`editedByUser` 由 `mapStory` 统一打标——所有用户编辑动作都经过它，导入流程不经过。
所以「用户改过」这个状态不需要每个 action 各自维护，加新编辑功能也不会漏。

## 6 落库（store 侧）

`importLibraryAssets` 只做拼接与重算，不再做任何判断：

- `visits`：按 `appends` 补 `mediaIds`、延后 `endAt`，再 concat 新到访；
- `stories`：按 `appends` 补 `mediaIds`、同步 `endAt`，**不动标题 / 封面 / 顺序**；
  `updatedAt` 会更新，但 `editedByUser` 不会被追加操作改成 `true`——不是用户改的；
- **`places` 的 `mediaIds` / `visitIds` 由底层数据重算**，不靠规划层维护。
  这是两次导入之间最容易对不上的两列，所以每次都整列重算，宁可多算一遍。
- **时间窗口**：新故事落在当前 `timeRange` 之外时，先切到**那张照片所在的那一天**，
  再按新的有效照片跨度收敛粒度（M12 起时间轴跟随有效照片，见 `docs/v5-visibility.md`）。
  不扩窗口的话，导入成功了却在地图和列表里都看不到，看起来像没导入。
- **地图归位**：`mapFocus` 带上第一个有定位的受影响地点的坐标，`token` 自增
  （同一坐标连续导入两次也要能触发第二次归位）。全部是未定位照片时不设，不让地图瞎飞。

## 7 存档 v1 → v2

v1 只存故事层，`places` / `visits` / `media` 每次从示例数据重建。导入会新建后三层，
所以必须一起存，版本 +1。

| 项 | v1 | v2 |
|---|---|---|
| `partialize` | 只 `stories` | `stories` / `places` / `visits` / `media` |
| 迁移 | — | v1 存档只交出 `stories`，三层由 `merge` 用示例数据补齐 |
| 校验 | `isValidStory` | 每层一个校验函数，任一层不合格就整层丢弃 |
| 声明了三层却为空 | — | 隔离备份 + 回退，不返回半截对象 |

`mapFocus`、`timeRange`、选中项、`lastMergedStoryId` 都**不进存档**——重启回到
「最近一次回忆所在月份」比恢复上次拖到的位置更符合预期。

## 9 已知限制

- **4 小时阈值没有实验标定。** 逛一整天回来会不会被切成 6 本，取决于实际拍摄节奏。
  调它只影响切分粒度，不影响「一次到访一本」和日期归属。
- **80 m 半径对城市里的高密度地点偏大。** 同一个商场里两家店会被并成一个地点。
  按需求这里选择「宁可并错，不要碎成一堆」——地点太碎地图上全是重叠标记。
- **地点名是「未命名地点 N」**，没有做逆地理编码。改名要用户自己来。
  编号依赖「已有导入地点数量」，把中间某个地点删掉之后，新地点可能重号。
- **视频只识别不导入。** 导入前会过滤掉非照片，结果面板里单列一条「跳过 N 个视频」。
- **导出临时文件仍可能触发 iCloud 下载**（逐张顺序读，比并发好压，但一张 48MP 的图仍然慢）。
- **导入进度不可中断后回滚。** 中途取消只停在这一张，已落库的不撤销——
  但重跑一次会被 `libraryAssetId` 判重，不会产生重复数据。
- **没有「预览这次导入会生成什么」。** 用户点确认之前看不到将生成几个地点几本故事，
  只能在结果面板里回看。加预览需要把规划层先跑一遍再问，属于下一步。
